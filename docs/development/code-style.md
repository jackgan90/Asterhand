# 代码风格与规模约束

状态：用户已确认。适用于手写产品代码、测试与脚本；文档也应按职责保持可读。

## 软阈值

| 对象 | 建议上限 | 统计 |
|---|---|---|
| 单文件 | 1000 行 | 物理行，含空行和注释 |
| 单函数 | 100 行 | 声明到函数结束的物理行，包含内部空行和注释 |

超过才触发超限评估，达到阈值本身不违规。生成代码和第三方代码可明确排除。工具应报告分类和位置，禁止通过压缩格式或拼接多条语句规避统计。

这两条不是硬性限制。逻辑高度内聚、拆分反而破坏理解时可以例外，但必须说明具体原因，而不是写“暂时不拆”。

## 文件超限后的用户确认

1. 开发新增内容使文件超过 1000 行，或继续向已超限文件添加内容时，agent 主动评估职责和拆分安全性。
2. 若可安全结构化拆分，向用户说明当前规模、职责问题、建议文件结构、依赖变化和验证方式。
3. **用户同意后才实施该拆分**。没有答复不是批准；不先拆完再请求追认。
4. 若无法安全拆分或拆分会降低可读性，在 feature 计划记录证据、理由与后续触发条件。

权限确认只针对这里要求的超限文件拆分，不自动扩大成所有普通编辑都需逐次批准。

## 拆分原则

- 按业务职责、生命周期和依赖方向拆分，避免 master class / god object。
- 内聚逻辑留在一起；不为了短文件产生大量无意义 wrapper 或全局状态。
- 保持公开行为不变，优先清晰数据流与窄接口。
- 避免循环依赖，明确模块所有权。
- 按行为风险运行相关回归，不写仅镜像实现的测试。

## 例外记录

在对应 feature 计划记录文件/函数、当前行数、内聚性理由、拆分代价、评估结论，以及用户同意的拆分范围（如适用）。后续相关变更重新评估。

格式工具采用各语言标准工具，具体版本随工具链建立。代码规模检查是提醒加审查机制，不是自动按行数拒绝交付。
