# Feature 开发流程

本流程为强制要求。依据 [AGENTS.md](../../AGENTS.md) 和 [开发需求](requirements.md)。

## 1. 明确范围

建立 `features/<descriptive-feature-name>/plan.md`，使用 [模板](templates/feature-plan.md)。记录需求 ID、用户目标、非目标、依赖、验收和涉及领域。确认当前授权涵盖所需实现，不将文档待办视为授权。

## 2. 先更新设计

补齐领域 requirements/design；重要架构取舍新增 ADR。明确已接受决定和待验证细节，不用未经验证的第三方 API 名称作为既定接口。

每个 feature 必须更新相关领域权威文档，不能只新增工作日志。实现前后的变更可以在同一交付单元中迭代，但交付时文档必须反映最终行为。

## 3. 实现与持续同步

实现获授权功能，按职责保持窄模块。发现范围、协议、配置、权限或恢复语义改变时同步文档；影响核心目标的变化先说明并取得相应决策。

新增内容后检查文件/函数规模，按 [代码风格](code-style.md) 处理超限。可安全拆分的超限文件先提方案，得到用户同意再改。

## 4. 验证

运行与变更相关的测试，按 [测试设计](../testing/design.md) 分层。运行记录包含真实环境、版本、命令、passed/failed/skipped/blocked、限制与证据；原始执行记录保存在忽略目录或版本发布物。长期文档只保留可复现方法和支持边界。无法运行的平台不是成功。

对外行为改变时同步验收步骤；安装变化必须包含干净环境或受控安装证据；任务语义变化必须包含对应故障测试。

## 5. 完成条件

- 需求和范围有追溯，实际行为符合约定。
- 相关领域 requirements/design 已同步，必要 ADR 已记录。
- 接口、配置、安装、测试和用户验收说明与实现一致。
- 相关验证已执行，未运行项及发布阻塞已说明。
- 规模例外理由明确；触发的文件拆分经过用户同意。
- feature 计划和路线图更新，交接包含下一步。
- 无凭据、个人运行数据或未授权依赖 / 平台变更。
- 文档使用明确的功能名称，引用受版本控制的文件；清除临时验证流水、本机路径、失效候选状态和会话交接信息。

实现完成、工程验证、用户验收、提交、推送、发布分别报告。没有文档更新的 feature 不得完成；无需为了文档要求虚构新需求或 ADR。
