# 原始使用场景 U01—U07

以下保留原草稿场景说明作为需求来源，历史措辞不定义当前首版范围。当前产品验收见 [V01—V06](../testing/acceptance.md)。

| 场景 | 当前处理 |
|---|---|
| U01 本机文件搜索 | 统一工具入口保留；首版必验收为创建/读取，Everything 后置可选 |
| U02 远程编码 | 远端执行可靠性首版实现，具体编码与 harness 后置 |
| U03 多仓库更新 | 后置，保留 VCS 与补偿需求 |
| U04 编码记忆 | 后置，先维护可迁移工程文档 |
| U05 定时与上线触发 | 后置 |
| U06 多角色 | 首版通用助手，其他角色后置 |
| U07 手机与渠道 | 首版响应式 Web，微信与主动推送后置 |

### U01：本机自然语言工具入口

用户在 Windows 上说：“帮我全盘搜索名为 test.txt 的文件，并返回结果。”

期望：

- 助手理解为精确文件名查询。
- 调用 Everything 等本机工具。
- 返回匹配路径。
- 能说明实际覆盖的卷、未搜索位置和索引状态。
- 不要求每次重新生成一个全盘遍历脚本。

对应需求：R03、R04、R13、R14。

### U02：远程编码与进度监控

用户在 A 上说：“让 B 给网站项目增加一个搜索功能。”

期望：

- B 接收任务并使用自己的开发环境与凭据。
- B 调用本机 coding harness。
- A 可以查看阶段、工具操作、错误、待回答问题和结果。
- B 已接收任务后，A 离线不终止 B 的正常执行。
- A 重连后可以查询任务与遗漏进度。
- 最终结果包括实际变更及验证信息。

对应需求：R05、R06、R08、R09、R10。

### U03：多仓库更新

用户说：“把游戏项目所有仓库更新到指定目标状态。”

长期期望：

- 知道项目涉及哪些仓库及其依赖。
- 理解目标分支、标签或 commit。
- 识别本地改动和冲突。
- 在必要时编写脚本。
- 保存恢复信息。
- 出现部分失败时，能按既定策略停止、补偿或回滚。
- 返回每个仓库的最终状态。

对应需求：R11、R12。

仓库类型尚未确认。首个适配器可选择 Git；如果实际项目包含 SVN，需单独建模和适配，不能将所有仓库默认视为 Git。

### U04：编码记忆管理

期望助手帮助记录和使用：

- 项目约定、构建方式与重要架构事实。
- 当前任务的进展和未解决问题。
- 相关 commit、worktree 和 harness 会话标识。
- 下一次继续工作需要的上下文。

“memory manager”是否还要直接维护各 harness 的特定记忆文件，留待后续确定。

对应需求：R15、R23。

### U05：定时和上线触发的维护

例如：

- 定时检查或更新仓库。
- 节点重新上线后补执行一次待处理维护。
- 定时收集新闻。

调度规则、离线补执行和任务归属需要明确定义。

对应需求：R16、R21、R22。

### U06：多角色助手

同一节点或不同节点可以提供 coder、语言教师、新闻收集等角色。

用户期望角色可以使用各自适合的模型、工具和知识，并根据节点在线情况分配新工作。

对应需求：R17—R24。

### U07：手机与通信软件入口

用户可以从手机或微信发指令、查看结果、了解任务进度。

远程问题与审批是跨节点任务的交互闭环；首版可以先用手机浏览器实现，无需同时开发原生 App 和微信渠道。

对应需求：R02、R09、R25。
